# Axoloti→Daisy Shim Instructions

## File Roles

- `main.cpp`: THE runtime — audio callback, init sequence, MIDI polling. All hardware interaction lives here.
- `axoloti_compat.h`: Force-included master header replacing xpatch.h. Include order matters.
- `xpatch.cpp`: NEVER edit — machine-generated from Ksoloti patcher.
- `STM32H750IB_flash.lds`: Patched linker script — only change is `.sdram` section mapping.

## When Adding New Shim Support

1. Find what Axoloti API the object uses (check ksoloti/src/main/java/generatedobjects/)
2. Add minimal stubs or implementations to existing headers
3. If it's a new subsystem, create a new header and add it to axoloti_compat.h
4. Test with `make clean && make CPP_SOURCES="src/main.cpp xpatch.cpp"`

## Init Sequence (main.cpp)

1. hw.Init() → DaisySeed hardware
2. SetAudioBlockSize(16) + 48kHz
3. sdram_init(0xC0000000...) → first SDRAM init
4. generate_lookup_tables() → sine2t, pitcht, etc.
5. RNG enable
6. ADC init (if NUM_ADC_CHANNELS > 0)
7. MIDI init
8. xpatch_init(PATCH_FWID) → calls xpatch_init2 which corrupts sdram_init
9. sdram_init(0xC0000000...) → RE-INIT after xpatch_init (critical!)
10. hw.StartAudio(AudioCallback)
11. MIDI polling loop

## Debugging No-Sound Issues

Check in order:

1. PATCH_FWID matches? (grep compile command for -DPATCH_FWID)
2. Q31 scaling in AudioCallback? (2147483648.0f not 134217728.0f)
3. \_pbss aliased correctly? (nm shows same address for start/end)
4. sdram_init re-called after xpatch_init?
5. .sdram section in linker script?
